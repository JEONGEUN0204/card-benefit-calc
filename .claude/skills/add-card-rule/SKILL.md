# 카드 약관을 규칙 JSON으로

추출이 틀려도 결과는 그럴듯한 숫자로 나온다. 그래서 이 작업의 핵심은 "뽑아내기"가 아니라
**근거를 남기고 골든 케이스로 못 박기**다. 골든 케이스 없이 추가된 카드 규칙은 검증되지 않은
추측이다.

## 0. 자료가 충분한지 먼저 본다

**자료는 사용자가 이 대화에 직접 준다.** 화면에는 카드를 들이는 길이 없으므로 요청문이
넘어오는 일도 없다. 대개는 혜택 안내 링크 하나로 시작하는데 그것만으로는 모자라니,
**상품설명서(약관) 원본을 먼저 요청한다.** 사용자가 그 파일을 대화에 첨부하면 된다.

혜택 안내 페이지에는 할인율과 대략적인 월 한도까지만 있다. 정작 계산을 좌우하는 항목은
상품설명서의 각주와 표에 있다.

| 항목 | 마케팅 링크 | 상품설명서 |
|------|------------|-----------|
| 할인율·대략적 한도 | 있음 | 있음 |
| `excludeFromSpending` | 거의 없음 | 각주에 있음 |
| 구간별 한도표 | 요약만 | 표로 있음 |
| `spendingExclusions`·`minTransaction`·`countLimit`·`rounding` | 없음 | 있음 |

PDF를 받으면 파일 그대로 읽는다(`Read` 도구의 `pages`). 미리 뽑아 둔 글자를 받지 않는 이유는
표다 — 텍스트 추출은 표를 줄로 풀어 칸의 순서를 흐트러뜨리고, 구간별 한도가 바로 그 표다.

원본을 구할 수 없다면, 채운 항목과 **채우지 못한 항목을 구분해 보고한다.** 어느 표를 못 봐서
무엇이 비었는지까지 적는다. 빈 자리를 그럴듯한 값으로 메우면 오류 없이 틀린 규칙이 된다.

## 1. 스키마 채우기

`src/core/types.ts`의 `CardRule`이 정답지다. 필드를 채울 때마다 약관의 어느 문장을 근거로
삼았는지 확인한다.

| 필드 | 약관에서 찾을 표현 |
|------|------------------|
| `tiers` | "전월 이용금액 30만원 이상", "직전 1개월 사용액" |
| `monthlyCapByTier` | "월 1만원 한도" — 구간마다 다른 경우가 많으니 구간별로 전부 적는다 |
| `totalMonthlyCapByTier` | "통합 할인한도", "월 최대 할인금액" |
| `minTransaction` | "건당 5천원 이상" — "이상"은 경계 포함이다 |
| `perTransactionCap` | "1회당 최대 1천원" |
| `countLimit` | "1일 1회", "월 3회" |
| `excludeFromSpending` | 아래 2번 참고 |
| `spendingExclusions` | "실적 산정 제외 대상" 목록 — 상품권·세금·공과금·무이자할부가 단골 |
| `rounding` | "10원 미만 절사" (대부분 `floor10`) |

## 2. `excludeFromSpending`을 가장 조심스럽게 읽는다

이 필드 하나가 필요 사용액을 수십만 원 단위로 바꾼다. 가장 자주 잘못 읽히는 곳이기도 하다.

- `"full"` — "할인받은 **이용금액**은 실적 산정에서 제외" → 결제액 전체가 빠진다 (한국 카드 다수)
- `"discountOnly"` — "할인받은 **할인금액**은 제외" → 할인액만 빠진다
- `"none"` — 제외 문구 없음

"이용금액"과 "할인금액" 중 어느 쪽인지 확실하지 않으면 **추측하지 말고 사용자에게 원문을
보여주며 묻는다.** 그리고 판단 근거가 된 문장을 `sourceNote`에 그대로 인용한다.

```json
"sourceNote": "전월 이용금액 30만원 이상 시 카페 업종 10% 청구할인. 건당 5천원 이상 결제 건에 한하며 월 1만원 한도. 할인받은 결제 건은 다음 달 실적 산정에서 전액 제외."
```

애매한 필드가 남았다면 추출을 멈추지 말고, 가정한 값과 그 이유를 사용자에게 함께 보고한다.
사용자가 검수해 고치는 것이 이 구조의 전제다.

## 3. 골든 케이스를 최소 2개 만든다

`fixtures/cases/`에 새 카드를 쓰는 케이스를 추가한다. **기대값은 손으로 계산해서 넣는다.**
엔진을 돌려 나온 값을 그대로 붙여넣으면 그 케이스는 아무것도 검증하지 못한다.

최소 구성:

1. **혜택이 열리는 구간** — 한도가 소진되는 지점까지 거래를 넣어 `cappedBy`와
   `benefitCapReached`가 나오게 한다
2. **혜택이 잠기는 구간** — 전월실적이 모자랄 때 `tierLocked`가 나오는지 본다

통합 한도가 있는 카드라면 통합 한도가 혜택별 한도보다 먼저 바닥나는 케이스를 하나 더 넣는다.
`description`에는 무엇을 검증하는 케이스인지와 기대값을 어떻게 계산했는지 적는다.

## 4. 검증

```bash
npm test
npm run sim -- fixtures/cases/<새-케이스>.json
npm run sim -- --max fixtures/cards/<새-카드>.json
```

`--max` 출력이 카드사 안내문의 "월 최대 할인금액"과 맞는지 대조한다. 여기서 어긋나면 구간별
한도나 통합 한도를 잘못 읽은 것이다. 카드사가 혜택별 한도의 단순 합을 광고하는 경우도 있으니,
`통합 한도에 잘림` 표시가 뜨면 그 차이가 설명되는지 확인한다.

마무리는 `verify-calc` 스킬의 경계 점검을 따른다.

## 5. 스키마에 자리가 없으면 멈춘다

표현할 수 없는 조건을 **가장 가까운 값으로 끼워 맞추지 않는다.** 무엇이 막혔는지 사용자에게
알리고, 계산 엔진을 넓힐지 함께 정한다. 부정확하게 넣으면 오류 하나 없이 그럴듯한 숫자가
나오고, 그게 이 도구에서 가장 나쁜 실패다.

지금까지 확인된 빈자리:

- **비율 제외** — "할인 받은 매출의 50%는 실적에 포함되지 않습니다". `ExclusionMode`는
  `full`/`discountOnly`/`none`뿐이라 비율이 없다
- **리터당 할인** — "주유 리터당 60원". `DiscountSpec`은 `rate`도 `amount`도 아닌 값을
  담지 못하고, 유가는 매달 바뀐다("정유사 공시 기준 휘발유가로 적용"). 토스 신한 Mr.Life의
  4대 주유소 할인이 여기 걸려 빠졌는데, 같은 한도를 할인마트와 나눠 쓰는 혜택이라 주말 할인이
  실제보다 덜 차게 된다
- **유실적 조건** — "전월 이용금액 유실적 고객님께"(1원 이상). 구간은 금액 하한으로만 나뉘어서
  "0원 초과"를 적을 자리가 없다. 구간을 하나 더 두면 다른 혜택의 한도표가 모두 늘어난다.
  Mr.Life의 인테이크몰 20%가 여기 걸려 0 구간에도 켜 둔 채 `sourceNote`에 적었다
전부 계산 엔진 변경이라 `verify-calc` 스킬과 골든 케이스 재계산이 따라온다.

**해결된 것:**

- 그룹 통합한도(혜택 여럿이 나눠 쓰는 한도) — `CardRule.capGroups` + `Benefit.capGroup`.
  예시는 `fixtures/cards/toss-samsung.json`
- **한도 없음** — 혜택의 `monthlyCapByTier`에 `null`. 키를 빼면 0(혜택 없음)이니 헷갈리지
  않는다. 공동 한도에 든 혜택과 공동·통합 한도표에는 `null`을 쓸 수 없다(`parseCardRule`이 막는다)
- **월정액 리베이트** — `CardRule.monthlyRebateByTier`. 거래와 무관하게 구간이 정하고, 한도에도
  실적에도 잡히지 않는다
- **할인 대상 제외** — `MatchRule.excludeCategories`·`excludePaymentTypes`. "무이자할부·공과금은
  할인 제외"처럼 할인에서만 빠지는 조건. 실적에서도 빠진다면 `spendingExclusions`에도 따로 적는다

세 가지의 예시는 `fixtures/cards/woori-every1.json`.
- **택1 선택지** — `CardRule.choices` + `Benefit.choice`. "4개 Pay 중 택1"을 혜택 넷으로 다 켜면 월 최대가
  부푼다. 계산 전에 `resolveChoices`로 좁히고, 골든 케이스에는 `choices` 필드로 고른 값을 적는다
- **중복 적용** — `Benefit.stackable`. "○○ 할인과 중복 적용 가능"이라고 적힌 쪽에 붙인다

두 가지의 예시는 `fixtures/cards/kb-need-pay.json`.
- **해외 결제** — `MatchRule.overseas`. `true`는 해외 결제만, `false`는 국내만("국내 가맹점 이용 시
  제공"). 거래의 해외 표시는 명세서 포맷(`isOverseas`)이 붙이므로, 해외 표기가 없는 카드사 명세서에서는
  해외 혜택이 잡히지 않는다는 것을 `sourceNote`에 적는다. 해외 할인이 실적 제외 목록에 있는지 따로
  확인한다 — 토스는 없고 NEED Pay는 있다
- **요일 조건** — `MatchRule.weekdays`. "주말할인서비스는 토요일/일요일에 해당되며 그 외 공휴일은
  해당되지 않습니다". 요일은 거래 날짜에서 나오므로 명세서가 따로 적어 줄 필요가 없다
- **시간대 조건** — `MatchRule.hours`. "승인시간 기준으로 오후 9시부터 오전 9시까지"는
  `{ "from": 21, "to": 9 }`다(`from` 포함, `to` 미포함, `from`이 크면 자정을 넘는 구간).
  승인 시간은 `Transaction.time`이 있을 때만 붙고, **지금 지원하는 명세서에는 승인시간 컬럼이
  없다** — 시간 조건이 붙은 혜택은 내 명세서로 돌리면 한 건도 걸리지 않는다는 것을 `sourceNote`에
  적는다. 구간별 최대 할인표는 한도만 보므로 영향받지 않는다
- **횟수 제한 두 겹** — `Benefit.countLimit`에 배열. "일 1회/월 5회 할인 적용"처럼 제한이 둘이면
  둘 다 적는다. 하나만 적으면 어느 쪽을 골라도 할인이 실제보다 많게 잡힌다

세 가지의 예시는 `fixtures/cards/shinhan-toss-mrlife.json`.
