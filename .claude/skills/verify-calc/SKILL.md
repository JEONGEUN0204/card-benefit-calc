# 계산 엔진 검증

할인 계산은 틀려도 조용히 틀린다. 숫자가 그럴듯하게 나오기 때문이다. 그래서 "테스트가
통과했다"로 끝내지 않고, 경계에서 무슨 일이 벌어지는지를 매번 확인한다.

## 1. 테스트와 타입

```bash
npm test
npm run typecheck
```

골든 케이스가 깨졌다면 **기대값을 결과에 맞추기 전에 약관을 다시 읽는다.** 골든 픽스처는
손으로 계산한 값이 유일한 기준이라서, 결과에 맞춰 기대값을 고치는 순간 앵커가 사라진다.
엔진이 맞고 픽스처가 틀렸다고 판단했다면, 왜 그런지를 케이스의 `description`에 남긴다.

## 2. 경계 점검

수정한 부분과 겹치는 항목을 골라 확인한다. 각 항목마다 `fixtures/cases/`에 대응하는
케이스가 있는지 보고, 없으면 만든다.

## 3. 눈으로 대조

숫자가 말이 되는지는 사람이 봐야 안다. 표를 펼쳐 손 계산과 맞춰본다.

```bash
npm run sim -- fixtures/cases/07-three-month.json
npm run sim -- --max fixtures/cards/toss-samsung.json
npm run sim -- --required fixtures/testcards/simple-cafe.json --tier 300000
```

특히 볼 것:

- **할인을 많이 받은 달의 실적이 줄어드는가.** 이 상호작용이 이 도구의 존재 이유다.
  할인액과 실적이 함께 늘어난다면 `excludeFromSpending`이 반영되지 않은 것이다.
- **`reason`이 사용자에게 설명이 되는가.** "해당 혜택 없음"과 "실적 구간 미달"은 사용자가
  할 행동이 전혀 다르다. 한도에 잘린 건은 `cappedBy`가 어떤 한도인지 말해줘야 한다.
- **필요 사용액에서 `실적 = 결제액 - 제외액`이 맞아떨어지는가.** 어긋나면 가상 거래 생성이
  비중이나 건단가를 잘못 쪼개고 있다는 뜻이다.

## 4. 불변 규칙 확인

`CLAUDE.md`의 불변 규칙 중 이번 수정이 건드린 것이 있는지 본다. 특히 자주 깨지는 둘:

- 할인액 계산에 `Math.floor`/`Math.round`를 직접 썼는가 → `roundDiscount`를 거쳐야 한다
- `src/core/`에 DOM·파일시스템·네트워크 의존이 들어갔는가 → 들어가면 브라우저 전용 구조가 깨진다

```bash
grep -rn "Math\.\(floor\|round\)" src/core --include=*.ts | grep -v rounding.ts
```

`requiredSpend.ts`의 예산 배분과 이분탐색에는 정상적인 `Math.round`/`Math.floor`가 있다.
할인액에 쓰였는지만 보면 된다.
